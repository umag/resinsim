# `sim.json` schema (v2)

Canonical interchange schema for resinsim's simulation output. Governed by
[ADR-0015](../../docs/adr/0015-sim-json-canonical-interchange.md) and
[ADR-0019](../../docs/adr/0019-voxel-field-on-disk-persistence.md) (the v1 → v2
clean break).

## Files

| File | Role |
| --- | --- |
| `v2.ts` | Canonical zod 4 schema, used for TS-side type inference and downstream LLM-tooling consumption. Hand-edited. The eleven object schemas that appear as `$defs` in `v2.schema.json` carry `.meta({ id })`; the root carries `.meta({ title, description })`. |
| `v2.schema.json` | JSON Schema (Draft 2020-12), generated by `npm run regenerate-schema` and committed. **The Rust ↔ JSON Schema parity test (`crates/resinsim-core/tests/sim_json_schema_parity.rs`) is the load-bearing drift guard** — fresh Rust serde output must validate against this file. |
| `package.json` | Pins `zod 4.0.0` (exact) plus the regenerate-schema toolchain. `@types/node` is pinned exact too — it's required for `tsc` to resolve the `node:fs`/`node:path`/`node:url`/`node:test` imports used by the script and the test. |
| `package-lock.json` | Committed. The three direct deps are exact-pinned, but their transitives (`esbuild`, `get-tsconfig`, `resolve-pkg-maps`, …) are not; the lockfile is what actually closes that hole. |
| `tsconfig.json` | Minimal Node-ESM config for `npm run typecheck`. Deliberately excludes `archive/` — the archived v1 schema is a historical record, not maintained code. |
| `scripts/regenerate-schema.ts` | `tsx` wrapper around `z.toJSONSchema(SimulationEnvelopeV2, …)`. Runs with `io: "input"`, `reused: "ref"`, and a post-generation `override` that stamps `additionalProperties: true` on every object node and strips the stray `id` key zod leaves on tagged `$defs`. See "Drift posture" below. |
| `tests/parse-goldens.test.ts` | `node:test` guard. Parses the three committed `crates/resinsim-inspect/tests/fixtures/sim_golden/*.sim.json` fixtures against `v2.ts` and asserts things the Rust parity test structurally cannot (tri-state `cure_kinetics_ea_is_default`, `base_force_n`'s default, unknown-key tolerance, a type-tamper negative, and — 2026-08, schemas-v2-missing-optional-fields — injected `layer_height_provenance`/`peel_shape_factor` acceptance and rejection against `v2.ts` SOURCE rather than the generated schema). Reads only — never writes the goldens. |
| `archive/` | Historical `v1.{ts,schema.json}`, preserved for reference per ADR-0019's clean break. Not maintained, not typechecked. |

## Drift posture

`v2.schema.json` is generated from `v2.ts` by `npm run regenerate-schema` and
committed. There are two documented drift surfaces:

1. **Rust serde ↔ `v2.schema.json`**: Caught by
   `crates/resinsim-core/tests/sim_json_schema_parity.rs`, run as part of the
   local verification battery (this repository has no `.github/` — there is
   no separate CI system; "the battery" is `cargo nextest run` plus the
   commands below, run locally). It fails loudly if a fresh
   `save_with_provenance(...)`/`save_stamped(...)` output does not validate
   against the committed `v2.schema.json`. This is the load-bearing risk,
   and it is fully automated.
2. **`v2.ts` ↔ `v2.schema.json`**: Now *checkable* by one command
   (`npm run regenerate-schema` followed by `git diff --exit-code
   v2.schema.json`), but not automated — nothing runs `npm` as part of the
   local battery today. Authors editing `v2.ts` are responsible for either
   (a) running `npm install && npm run regenerate-schema` and committing the
   updated `v2.schema.json`, or (b) hand-aligning `v2.schema.json` directly
   and noting the residual here. The parity test still catches drift
   transitively on the next Rust-side change either way.

Because zod's default `io: "output"` mode emits `additionalProperties:
false` on every object — which would silently narrow the published
contract and reject real Rust-produced envelopes carrying fields `v2.ts`
doesn't declare — the regenerate script does not use zod's defaults. It
passes `io: "input"` (so `.default()` fields like `base_force_n` don't get
promoted into `required`), `reused: "ref"` (so the `.meta({ id })`-tagged
schemas land in `$defs` under their human names instead of being inlined),
and an `override` hook that stamps `additionalProperties: true` explicitly.
This is why regenerating is not a config-free operation — the options are
load-bearing, not stylistic.

Future work: integrate the regenerate script into a CI step (once one
exists) that fails on `git diff --exit-code` after a fresh regenerate.
Tracked as a follow-up, out of scope for this lifecycle.

## Bumping schema_version

Producer-side breaking changes (rename, remove, retype, integer-discriminant
reorder) require a new version. Procedure:

1. Copy `vN.ts` → `vN+1.ts` (the v1 → v2 step already happened; see
   ADR-0019). Edit the new file to match the new shape.
2. Bump the literal in `SimulationEnvelopeVN+1` to `N+1`.
3. Bump `CURRENT_SCHEMA_VERSION` in `crates/resinsim-core/src/repositories/simulation_repo.rs` to `N+1`.
4. Regenerate `vN+1.schema.json` via `npm run regenerate-schema`.
5. Update the parity test in `crates/resinsim-core/tests/sim_json_schema_parity.rs`
   to validate against `vN+1.schema.json`.
6. Document the breaking change in `ADR-0015`'s Versioning Examples section.

Old `vN.{ts,schema.json}` files stay in the tree (or move to `archive/` on a
clean break, per ADR-0019); consumers branching on `schema_version` keep
working with old envelopes.

## Additive (non-breaking) changes

Adding an optional field is additive — no version bump required. Edit
`v2.ts`, regenerate `v2.schema.json`, ship. (`peel_shape_factor` + five
Tier-2 `LayerResult` fields + `layer_height_provenance`, 2026-08 /
schemas-v2-missing-optional-fields, is the most recent example;
`cure_kinetics_ea_is_default`, 2026-08 / KB-153, is the prior one.)

## Regenerating `v2.schema.json`

```sh
cd schemas/sim-json
npm install
npm run typecheck
npm test
npm run regenerate-schema
git diff --exit-code v2.schema.json   # expect clean if v2.ts didn't change
```

The regenerated file is committed alongside the `v2.ts` change.

## Pinning policy

Every dependency in `package.json` is an exact version (no caret, no tilde),
and `package-lock.json` is committed so transitive dependencies can't float
either. Drift in zod's JSON-Schema output (e.g. between zod 4.0.0 and 4.1.0)
would otherwise silently change `v2.schema.json`'s shape and could mask Rust
serde drift behind a moving baseline.

## Cross-language drift guard

Two independent guards cover the two directions of drift:

- `crates/resinsim-core/tests/sim_json_schema_parity.rs` produces a known
  `SimulationEnvelope` via Rust, serializes it, and validates the output
  against `v2.schema.json` using the `jsonschema`/`boon` crate. Any drift
  between the Rust serde shape and the JSON Schema fails this test
  immediately.
- `schemas/sim-json/tests/parse-goldens.test.ts` parses the committed
  `crates/resinsim-inspect/tests/fixtures/sim_golden/*.sim.json` fixtures —
  real, Rust-produced envelopes — against the zod source (`v2.ts`) directly.
  This is the other direction: it validates that `v2.ts` itself (not just
  the generated JSON Schema) accepts real Rust output, including fields
  Rust serialises that `v2.ts` doesn't declare. Note the coupling: this test
  reaches from `schemas/` into `crates/resinsim-inspect/tests/fixtures/`
  because those goldens are the only committed real envelopes in the repo —
  a future fixture move needs to update `FIXTURE_DIR` in that test.
